# Release-to-distribution drafts

The workflow deliberately separates **content generation** from **external publishing**.
No command in this repository calls GitHub, Brevo, a social network, DNS, or a deployment
provider.

## Flow

```text
owner review + explicit approval
        ↓
manifest: RELEASED + releaseApproval + dates
        ↓
pnpm validate:effects / pnpm verify
        ↓
pnpm drafts [--slug=…]                  # deterministic local files
        ↓
manual review of every draft
        ↓
separate owner decision to publish/send/deploy
```

The generator is `scripts/draft-release.ts` plus `lib/publishing/drafts.ts`.

## Commands

```sh
# Internally review a candidate that is not released.
pnpm drafts -- --review --slug=ascii-waves

# After an effect is RELEASED in the manifest, generate release drafts.
pnpm drafts -- --slug=ascii-waves

# All released effects.
pnpm drafts

# Pin the date used in the drafts and directory.
pnpm drafts -- --slug=ascii-waves --date=2026-10-30

# Output location (gitignored):
drafts/<date>/<slug>[-review]/
```

If no effect is released, the default command exits with code 2 and a clear message. This
is expected in V0.1. The current candidate’s internal review drafts are kept in
`evidence/drafts/ascii-waves-review/` as evidence.

## Generated files

| File | Contents | External action |
| --- | --- | --- |
| `github-release.md` | Release title, summary, technical note, requirements, install, provenance, license | None; copy manually to GitHub Releases after approval |
| `newsletter.md` | Subject, preview text, campaign body, unsubscribe reminder | None; no email is sent |
| `social.md` | Short post, thread opener, alt text | None; no post is made |
| `page-metadata.md` | Title, description, canonical, robots state | None |
| `sitemap-entry.txt` | Correct entry only if released | None; actual sitemap is generated by the app |
| `checklist.md` | Owner/distribution checks | None |
| `draft.json` | Machine-readable draft manifest | `distributionAuthorised: false` |

Every draft starts with one of these warnings:

- **INTERNAL REVIEW DRAFT — NOT FOR DISTRIBUTION** for unreleased effects;
- **OWNER APPROVAL REQUIRED BEFORE DISTRIBUTION** for released effects.

Unreleased drafts set `canonicalUrl: null` and do not contain an effect-page URL or sitemap
entry. A release draft contains the canonical URL but still has
`distributionAuthorised: false`.

## Owner approval requirements

Before a release draft is considered usable:

- [ ] The owner has reviewed the live effect and approved the art in writing.
- [ ] The approval is recorded in `releaseApproval` with a durable evidence path/URL.
- [ ] The status is `RELEASED`, `releasedAt` is set, and the updated date is correct.
- [ ] Source/media provenance and licenses are verified.
- [ ] The public effect page returns 200 at the canonical URL.
- [ ] The sitemap includes the effect only because it is released.
- [ ] Reduced-motion/fallback and desktop/mobile smoke checks pass.
- [ ] Social image/alt text has been inspected.
- [ ] Newsletter copy has been rendered in Brevo and manually proofread.
- [ ] A separate owner decision authorises the actual GitHub release, campaign send,
      social post and deployment.

The generator itself cannot satisfy these checks. See `docs/RELEASE-RUNBOOK.md`.

## Determinism and no side effects

- Date is explicit or derived from the run date; all draft copy is a pure function of the
  manifest and options.
- The builder refuses a release draft if status is not `RELEASED` or the approval record is
  absent.
- The builder validates the ISO date.
- It writes only to `drafts/`; existing generated files for the same date/path are
  replaced locally.
- It does not import an email or social SDK, and has no credentials.
- It does not modify the manifest, source, archive or site.

The unit suite covers the refusal path, warning text, canonical/sitemap behavior and the
`distributionAuthorised: false` invariant.

## Current state

`nwx-ascii-waves` is `OWNER_REVIEW`; no release draft is authorisable. Internal review
drafts are intentionally not distribution material. The gallery remains prelaunch and the
release gate remains open.

## Future automation boundary

If this ever expands, the safe next step is a reviewed GitHub Action that renders a
release page and opens a draft PR, not an autonomous sender. Any automation must still
require an explicit owner signal and a pre-send dry run.

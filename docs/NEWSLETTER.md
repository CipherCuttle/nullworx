# Nullworx Drops — newsletter operations

Status: **UI and adapter complete; live collection disabled; zero emails sent.**

Nullworx Drops is an optional, double opt-in newsletter. The V0.1 repository defaults to
`NEWSLETTER_PROVIDER=disabled`, in which case the endpoint stores nothing and returns an
“unavailable” message. The only working flow in this repository is an in-memory mock used
by tests and local review.

## Consent model

Two separate choices are stored:

| Category | UI label | Required? | Default |
| --- | --- | --- | --- |
| Free newsletter | “Send me Nullworx Drops: free effects, experiments, code notes and occasional bonus assets.” | Yes, for this list | Unchecked |
| Premium marketing | “Also send future premium pack announcements, launch offers and occasional promotions.” | No | Unchecked |

Premium marketing is never implied by free-newsletter consent. The server schema requires
`dropsConsent: true`; `premiumMarketing` defaults to `false`. The two flags are passed
separately to the provider and recorded as separate Brevo attributes. No prechecked box
exists in the UI or server defaults.

Consent evidence generated by the app:

```json
{
  "consentId": "uuid",
  "dropsConsent": true,
  "premiumMarketing": false,
  "source": "/drops",
  "version": "2026-10-28",
  "collectedAt": "ISO-8601 timestamp"
}
```

The app does not persist this object itself. It is passed to the provider; the Brevo
adapter writes the fields below as contact attributes. The mock keeps an in-memory copy
for tests. Brevo’s DOI event history is the provider-side confirmation record.

## Provider modes

| Mode | Behavior | Valid for public V0.1? |
| --- | --- | --- |
| `disabled` (default) | API returns 503; nothing stored/sent | Yes, safe default |
| `mock` | In-memory only; returns a local confirmation link; never sends email | Local/tests only |
| `brevo` | Real DOI via Brevo; provider sends confirmation/unsubscribe | Only after launch approval and configuration |

In production, `mock` is forced back to `disabled` unless
`NEWSLETTER_ALLOW_MOCK=1` is explicitly present. Do not set that flag on a public
deployment. Even with the flag, mock data is in-memory and not a subscriber database.

## Configuration

```sh
# Server-side only. Never prefix provider values with NEXT_PUBLIC_.
NEWSLETTER_PROVIDER=brevo
BREVO_API_KEY=...
BREVO_DROPS_LIST_ID=123
BREVO_DOI_TEMPLATE_ID=456
NEWSLETTER_CONFIRM_REDIRECT_URL=https://nulllworx.site/drops/confirmed

# Required for real production collection; at least 32 characters.
NEWSLETTER_IP_HASH_SECRET=...

# The canonical origin remains separately configured.
NEXT_PUBLIC_SITE_URL=https://nulllworx.site
```

The app disables Brevo mode unless all values are present. In production it disables
collection if the IP hash secret is missing or shorter than 32 characters. The
confirmation redirect must be the **canonical origin + `/drops/confirmed`**, with no query
or fragment and no different host. This is enforced in both the config and the Brevo
adapter, so a typo cannot redirect subscribers elsewhere.

`BREVO_API_KEY` is read only in server code (`lib/newsletter/config.ts` imports
`server-only`). It is never included in a client bundle.

## Brevo setup checklist

1. Create the Brevo account, complete account approval and accept the data-processing
   terms. The legal entity/DPA must be reviewed by the owner; the code does not claim a
   signed DPA.
2. Create the Drops list and note its numeric ID.
3. Create a double opt-in template and note its numeric template ID. Start from
   `emails/doi-confirmation.html`; add the owner’s legal/contact details before use.
4. Set the DOI redirect to `https://nulllworx.site/drops/confirmed` and configure
   `NEWSLETTER_CONFIRM_REDIRECT_URL` identically.
5. Create the custom attributes used by the adapter. Use **text** for timestamps so the
   adapter can store full ISO-8601 values and an empty string for an unset premium date:
   - `DROPS_CONSENT` (boolean)
   - `DROPS_CONSENT_AT` (text)
   - `CONSENT_VERSION` (text)
   - `CONSENT_SOURCE` (text)
   - `CONSENT_ID` (text)
   - `PREMIUM_CONSENT` (boolean)
   - `PREMIUM_CONSENT_AT` (text)
   - `UNSUBSCRIBED_AT` (text, optional but used by admin unsubscribe)
6. Authenticate the sending domain: SPF, DKIM, DMARC, and the provider’s domain
   verification. Use a real sender address.
7. Disable open/click tracking in campaign settings where possible. The DOI call passes
   `contactPixelTrackingConsent: false`, but that only governs the DOI recipient where
   the provider feature is enabled. Tracking policy must also be set at the account and
   campaign level.
8. Create a welcome automation only after DOI and consent records have been tested. The
   repository never sends it.
9. Configure the provider-managed unsubscribe/preferences link in all campaigns.

## API flow

### Subscribe — `POST /api/newsletter`

Request (JSON only; unknown fields rejected):

```json
{
  "email": "person@example.com",
  "dropsConsent": true,
  "premiumMarketing": false,
  "company": ""
}
```

Headers: `content-type: application/json`, optional `idempotency-key`. The browser sends a
random UUID. Cross-origin requests are rejected; non-browser requests without `Origin`
still face validation, consent, and rate limits.

Server sequence:

1. Reject non-JSON, oversize or malformed bodies; validate email and consent.
2. Same-origin check and honeypot. A honeypot submission returns a generic 202 but is
   never sent to the provider.
3. Load the configured provider; disabled returns a clear 503 with no storage.
4. Apply rate limits keyed by HMAC(IP) and SHA-256(email): 8 IP attempts / 10 min and
   3 email attempts / 10 min in one process.
5. Normalise email, build consent evidence and call the provider.
6. Return a generic 202 whether the address is new, pending, already confirmed,
   suppressed, or does not exist. Do not let the response reveal subscriber state.
7. Provider errors return a generic 502; details and secret values are not returned.
8. Log only request ID, outcome kind and provider mode.

Idempotency is cached for 15 minutes per process, keyed by the idempotency key and request
hash. Reusing a key with a different payload returns 409. The browser uses a unique key
per submission.

### Brevo adapter

`lib/newsletter/brevo-provider.ts`:

- looks up the contact by email;
- treats `emailBlacklisted` or Drops-list unsubscribes as suppressed (still generic 202);
- updates premium preference for an already-confirmed contact without resending DOI;
- calls `POST /v3/contacts/doubleOptinConfirmation` for new or pending contacts;
- normalises duplicate-request responses to the accepted/generic path;
- maps 401/403, 429 and other failures to typed errors without exposing the key;
- sets a timeout and uses server-side `fetch`.

The API body is aligned with the current official SDK request type:
`email`, `includeListIds`, `redirectionUrl`, `templateId`, `attributes`,
`contactPixelTrackingConsent`. Verify the provider’s docs before changing the adapter.

### Confirmation

Brevo owns the confirmation email and token. The visitor clicks Brevo’s link and is
redirected to `/drops/confirmed`. In the mock mode, a local HMAC-signed token is used:

```text
GET /api/newsletter/confirm?token=...
  -> 303 /drops/confirmed?preview=1
```

The confirmation page is noindex/no-store. A successful confirmation fires
`newsletter_confirmation_completed` (no email in the payload). The mock’s status page says
explicitly that no email was sent and no real subscriber exists.

### Unsubscribe and suppression

Brevo’s hosted unsubscribe/preferences link remains in every real campaign; the
application does not replace it. The adapter also has an owner-only `unsubscribe(email)`
method for administrative cleanup; **no public route exposes it**. It removes the contact
from the Drops list and clears both consent attributes without blacklisting all Brevo
messages.

The mock uses a one-year signed unsubscribe token to exercise the flow. Disabled and real
modes return 404 for the mock-only confirmation/unsubscribe endpoints.

## Email flows

Prepared copy is in `emails/`:

| File | Purpose | Sent by this repo? |
| --- | --- | --- |
| `doi-confirmation.html` | Brevo DOI template | No |
| `welcome.md` | Post-confirmation welcome automation copy | No |
| `new-drop.md` | Campaign draft skeleton | No |
| `preferences.md` | Unsubscribe/preference guidance | No |

V0.1 sends no confirmation, welcome, campaign or unsubscribe email. The Brevo adapter does
start a provider-side DOI request when explicitly configured; no live credentials are
present. A real send is an owner decision after the launch gates.

## Privacy, retention and deletion

Data requested: email address and the two consent choices/consent record. No name, phone,
postal address or account. Processors: the hosting provider (access logs), Brevo (email
delivery/DOI/suppression), and no analytics vendor. Brevo is a French provider; the owner
must review its DPA and subprocessors before collection.

Retention expectations:

- active subscribers: while subscribed and while Drops operates;
- unsubscribed: removed from the Drops list; a suppression signal may remain to prevent
  accidental re-email;
- consent evidence: only as long as needed to prove consent/meet legal obligations;
- unconfirmed DOI records: purge on a 30-day schedule (owner configuration; not automated
  in this repository);
- mock data: in-memory, vanishes on process restart;
- application logs: structured event/request-ID lines, no email or raw IP; host log
  retention is outside the app.

Requests for access, correction, export or deletion: the owner verifies the request and
acts in Brevo. A dedicated privacy mailbox is required before real collection. Do not send
identity documents to a public GitHub profile.

## Launch gates for real collection

All of these must be true before enabling Brevo in public:

- [ ] Owner has approved real subscriber collection in writing.
- [ ] Brevo account, DPA, sender domain, SPF/DKIM/DMARC and legal details are complete.
- [ ] Privacy mailbox and privacy-page entity details are live.
- [ ] List/template IDs and consent attributes exist.
- [ ] DOI redirect is the canonical `/drops/confirmed`.
- [ ] IP hash secret and all provider secrets are set server-side.
- [ ] A durable rate-limit/idempotency store is in place if running more than one instance.
- [ ] Mock/disabled modes are not exposed on the public deployment.
- [ ] A test DOI, welcome, unsubscribe and preference change are observed end to end.
- [ ] No campaign is sent until a separate owner approval and manual review.

## Remaining V0.1 limitations

- Rate limiting and idempotency are process-local; a multi-instance deployment would need
  Redis or another shared store.
- No admin UI for subscriber export/deletion; use the provider dashboard.
- No automated unconfirmed-record purge.
- No live-provider integration test (no credentials; would send email).
- Provider account approval, deliverability reputation and legal review are operational
  prerequisites, not code tasks.
